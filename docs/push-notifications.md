# Пуш-уведомления для расписания врачей — как это будет работать

Этот файл — простое объяснение идеи, без кода. Задача: после того как администратор загружает расписание на завтра, врачи получают на телефон уведомление «Расписание доступно» и по нажатию попадают на нужную страницу сайта.

Проект расписания полностью отдельный от электронной очереди. Очередь мы не трогаем вообще: ни ее базу, ни ее Redis, ни ее сервер. У расписания свой Django, своя база, свой сервер на VPS. Все, что описано ниже, живет только внутри проекта расписания.

## Общая схема в одном абзаце

Django остается главным. Он знает врачей, знает расписание и решает, кому слать уведомление. Android-приложение — это тонкая обертка над сайтом: внутри окно с сайтом, плюс умение принимать системные уведомления. Между ними стоит Firebase Cloud Messaging. Это почтальон: Django просит его доставить сообщение на конкретный телефон, а он доставляет.

## Почему сайт внутри телефона сам не может слать пуши в фоне

Приложение будет показывать сайт через WebView. Это просто окно браузера внутри приложения. Пока приложение открыто, сайт работает как обычно.

Но когда приложение свернуто или закрыто, система Android может его остановить. Надеяться, что открытая страница сама разбудит телефон, нельзя. Поэтому для фона используется отдельный системный механизм — Firebase Cloud Messaging. Он работает даже когда наше приложение закрыто, и именно он показывает уведомление в шторке.

Получается разделение: WebView — это интерфейс, а Firebase — это доставка уведомлений в фоне.

## Что делает телефон, а что делает сервер

Телефон делает мало: показывает сайт, получает свой адрес для пушей от Firebase, передает этот адрес серверу, принимает уведомления и открывает нужную страницу сайта по нажатию.

Сервер делает все остальное: хранит врачей и расписание, хранит адреса телефонов, после загрузки определяет, кто есть в файле, и просит Firebase разослать уведомления.

Firebase не знает ничего про врачей и пациентов. Для него телефон — просто адрес доставки.

## Откуда берется адрес телефона

Мы сами ничего не придумываем. Когда приложение с подключенным Firebase запускается, Firebase регистрирует эту конкретную установку приложения и выдает ей уникальный идентификатор.

В старых инструкциях он называется registration token. В новых Firebase постепенно переходит на Installation ID. Смысл одинаковый: это адрес данного экземпляра приложения на данном телефоне. Приложение получает его от Firebase и потом сообщает серверу.

## Когда приложение сообщает свой адрес серверу

Firebase может выдать адрес сразу при первом запуске. Но в этот момент мы еще не знаем, какой врач держит телефон в руках.

Поэтому привязывать адрес к врачу имеет смысл только после входа. Логика такая: приложение получило адрес и хранит его у себя, врач вошел на сайте, после этого адрес передается серверу и связывается с этим врачом. Плюс адрес повторно сверяется при запусках и при его изменении.

## Как система понимает, какой врач вошел

Это самый важный момент. Понимать это должен не телефон, а Django. И он уже это умеет.

Врач открывает приложение, видит обычную страницу входа нашего сайта и вводит логин и пароль. Django проверяет их и создает сессию. После этого окно с сайтом хранит куку сессии. Любой следующий запрос с этой страницы Django уже узнает: это Иванов.

То есть нам не нужно спрашивать у телефона, кто вошел. Django уже знает это по своей сессии.

## Как токен попадает от телефона на сервер

Здесь два разных шага, их легко перепутать.

Шаг первый вообще без Django и без интернета. Страница сама в Firebase не ходит и номер оттуда не забирает. Номер от Firebase получает только нативная часть приложения. Дальше телефон передает его странице локально, внутри себя. Это не запрос в интернет, а просто передача строчки от приложения странице через штатный мостик WebView.

Удобно думать так: телефон как будто подставляет номер в невидимое поле на странице. Скрипт страницы это поле читает и запоминает. Телефон сам с этим номером в интернет не ходит, он только отдает его странице.

Шаг второй — уже обычный запрос страницы к Django. Когда страница номер узнала, она сама обращается к серверу на адрес регистрации устройств и кладет в запрос только сам номер. Никакой фамилии, логина или номера врача телефон не сообщает.

А куку WebView прикладывает сам, как обычный браузер. Поэтому фраза «отправляем через страницу» означает: сеть идет со страницы, кука уже внутри, и Django видит владельца.

Итого цепочка: Firebase выдал номер телефону, телефон передал его странице внутрь, страница отправила его Django вместе со своей кукой.

Такой путь выбран специально, чтобы не городить вторую авторизацию для телефона. Если бы телефон слал номер напрямую своим собственным запросом в обход страницы, у него не было бы куки сессии, и сервер спросил бы «а ты кто». Пришлось бы вытаскивать куку из окна или делать отдельные ключи. Проще, когда отправляет уже авторизованная страница.

## Как страница опрашивает приложение

Да, JS внутри WebView умеет обращаться к объектам приложения, но только к тем, которые приложение само ему показало.

Приложение регистрирует объект под именем `AndroidBridge` (в коде — `MainActivity.kt`). JS видит не поля объекта, а только методы с пометкой `@JavascriptInterface`. У нас такой метод один — `getPushRegistration()`, он возвращает строчку с адресом. К остальному приложению у страницы доступа нет.

По этапам это выглядит так:

1. Приложение при запуске забирает у Firebase строчку с адресом и кладет ее себе в память.
2. Приложение открывает сайт и показывает странице объект `AndroidBridge`.
3. Врач входит на сайте, сайт выдает WebView куку сессии.
4. Страница вызывает `getPushRegistration()` и получает строчку. Сети здесь нет.
5. Страница отправляет эту строчку в Django на адрес регистрации. Кука прикладывается сама.
6. Django берет владельца из куки, адрес из запроса и записывает пару в базу.

Направление опроса — от страницы к приложению: страница спрашивает, приложение отвечает. Наоборот приложение странице ничего не pushes, поэтому ему не надо следить за загрузкой страниц.

## Как кука и токен соединяются

Кука — это паспорт. Токен — это новый номер телефона. Сервер на ресепшене записывает: этот номер принадлежит человеку с этим паспортом.

Django получает запрос и видит сразу две вещи вместе. Внутри запроса лежит записка с номером, а на конверте штамп-паспорт по куке. Паспорт он берет не из записки, а из сессии. Поэтому вывод простой: раз запрос пришел от Иванова и в нем лежит номер ABC123 — значит ABC123 принадлежит Иванову. Эта пара и сохраняется в таблице устройств.

Нам не надо склеивать их руками. WebView сам прикладывает куку к запросу страницы, а номер страница сама кладет в запрос. Django просто видит их вместе в одном запросе.

Если врач еще не вошел, штампа нет. Django видит анонимного пользователя и думает: номер знаю, владельца не знаю. Ничего не привязывает. После входа страница повторит отправку — и тогда будут и номер, и владелец.

## Куда именно отправляется адрес

В Django, а не в Firebase. С Firebase телефон уже пообщался через свой SDK и получил от него адрес. А вот кому этот адрес принадлежит — должен решать только наш сервер.

То есть цепочка такая: Firebase выдал адрес телефону, телефон через страницу передал его Django, а когда надо слать уведомление, уже Django обращается к Firebase с просьбой доставить.

Секретные права на отправку живут только на сервере. Телефону они не нужны.

## Что делает Django, когда получил адрес

На сервере будет отдельный закрытый адрес для регистрации устройств. Он работает только для вошедших.

Django получает адрес, смотрит на текущего пользователя по сессии и сохраняет связь: этот адрес принадлежит этому врачу. Чужие данные подделать нельзя, потому что номер врача от клиента вообще не принимается, владелец берется только из сессии.

## Как это хранится в базе

Не одним полем в карточке врача, а отдельной таблицей устройств. У каждого устройства указывается врач, сам адрес от Firebase, что это Android, активно ли оно и когда последний раз обновлялось.

Отдельная таблица нужна по простой причине: у одного врача может быть два телефона или телефон и планшет. Тогда у Иванова будет две записи, и уведомление придет на оба устройства.

## Что происходит, когда администратор загружает расписание

Администратор загружает файл на завтра. Django разбирает его и сохраняет в базу.

Дальше Django смотрит, какие врачи реально есть в этом файле. Сверка идет по уже существующему правилу: название колонки в таблице сравнивается со специальным полем в карточке врача, где написано, как этот врач называется в таблице. Пробелы, точки, регистр и буква ё при этом не важны. Это то же самое сопоставление, по которому врач сейчас видит вкладку «Моё расписание».

Только тем врачам, кто найден в файле, и положено уведомление. Остальным ничего не слать.

Важно, что уведомление отправляется только после того, как расписание успешно сохранилось. Иначе врач нажмет на пуш, а расписания еще нет из-за ошибки в файле.

Чтобы загрузка не висела, пока идут отправки, сама рассылка выносится в фон. Очередь при этом никак не используется. Для расписания будет свой отдельный фон, никак не связанный с очередью. Самый простой стартовый вариант — своя отдельная очередь задач только для расписания. Если ее пока нет, рассылку можно делать в отдельном фоновом потоке после сохранения, главное — не держать запрос администратора.

## Как Django просит Firebase доставить уведомление

На сервере подключается официальный серверный SDK Firebase для Python. Django готовит сообщение: короткий заголовок вроде «Расписание опубликовано», текст вроде «Расписание на завтра доступно» и невидимые служебные данные — какую страницу сайта открыть.

Дальше Django передает Firebase сообщение и список адресов тех врачей, кто был в файле. Firebase сам доставляет их на телефоны.

Само расписание через Firebase не едет. Через него едет только сигнал «появилось новое, открой вот эту страницу». Актуальные данные телефон потом заберет с нашего сайта.

## Что видит врач и что происходит по нажатию

Допустим, приложение закрыто. Firebase доставляет сообщение, телефон показывает уведомление в шторке.

Врач нажимает на него. Приложение открывается и смотрит в служебных данных, какую страницу сайта надо показать, например страницу расписания на завтра. После этого оно просто загружает этот адрес в том же окне с сайтом.

Если сессия врача еще жива, он сразу видит свое расписание. Если сессия истекла, сайт попросит войти, а после входа желательно вернуть его на ту же страницу расписания.

В самом уведомлении нет никаких медицинских данных и фамилий пациентов. Только факт, что расписание готово.

## Что понадобится подключить

На телефоне — официальный SDK Firebase для сообщений и стандартное подключение приложения к Firebase-проекту. Сам показ сайта делается обычными средствами WebView. Для современных телефонов нужно будет спросить у пользователя разрешение на показ уведомлений, без него шторка ничего не покажет.

На сервере — официальный серверный SDK Firebase для Python. Отдельно ради регистрации устройств ничего ставить не надо. Фоновая рассылка на старте может быть своей отдельной очередью только для расписания, очередь при этом не затрагивается.

## Подводные камни простыми словами

Адрес телефона не вечный. Он меняется при переустановке приложения, очистке данных и переносе на другой телефон. Поэтому приложение при запуске сверяет адрес с сервером, а сервер хранит время последнего обновления.

Переустановка дает новый адрес. После входа врача он привяжется заново, а старый со временем удалится, особенно когда Firebase при попытке отправки скажет, что такого адреса больше нет. Такие записи надо чистить.

Выход из аккаунта обязательно отвязывает устройство. Иначе следующий врач на том же телефоне будет получать чужие уведомления. Это особенно важно для медицины.

Несколько устройств — это нормально. У одного врача просто несколько записей в таблице устройств, и сообщение уходит на каждую активную.

Телефоны без сервисов Google не получат такие уведомления. На обычных телефонах проблем нет, но для отдельных Huawei это надо учитывать отдельно.

Мост между приложением и страницей надо открывать только нашему сайту. Чужые страницы в это окно загружать нельзя, иначе им тоже станет доступен этот мост.

## Один телефон — один текущий врач

Номер Firebase принадлежит не врачу, а установке приложения на конкретном телефоне. У него всегда один текущий владелец. Кто последним вошел на этом телефоне — тот и владелец.

Пример. Был Иванов, номер ABC123 записан на Иванова. Потом на этом же телефоне вошел Петров. Приложение не переустанавливали, поэтому номер тот же — ABC123. Но страница теперь работает по новой сессии Петрова и снова говорит серверу: запомни для меня ABC123. Django видит: номер старый, а владелец запроса новый. И переписывает связь: теперь ABC123 — это Петров, а не Иванов.

Поэтому правило простое: при каждом входе страница всегда отправляет текущий номер заново, даже если он не менялся. Именно этот повтор со свежей кукой и перепривязывает телефон к новому врачу.

Отсюда следует честное поведение для общего телефона. Если в новом расписании есть Иванов, но нет Петрова, а телефон сейчас у Петрова — пуш Иванову на этот телефон не придет. И это правильно: телефоном пользуется Петров, ему незачем видеть чужое уведомление и переходить в чужое расписание.

А что тогда с Ивановым? Он получит пуш на свои остальные устройства, где он все еще залогинен. Если у него был только этот один общий телефон — он ничего не получит, пока снова не войдет. Пуши всегда идут только текущему пользователю телефона.

Делать на одном телефоне сразу двух получателей, чтобы каждый получал свое, мы не будем. Это уже сложная схема с выбором профиля. Считаем: один телефон в один момент времени — один врач. Кто вошел последним, тот и получает.

## Что уже сделано в коде

Таблица устройств `PushDevice` в приложении `accounts`: врач, адрес Firebase, платформа, активность, время обновления. У одного врача может быть много устройств.

Адреса сервера: `POST /api/push/register/` привязывает адрес к текущему пользователю по сессии, `POST /api/push/unregister/` гасит его при выходе. Номер врача от клиента не принимается.

Страница на сайте сама забирает адрес у приложения через мост `AndroidBridge.getPushRegistration()` и отправляет его в Django. При каждом входе отправка повторяется, даже если адрес не менялся — так общий телефон перепривязывается.

Получатели считаются по уже существующему сопоставлению названий: ключ колонки версии сравнивается с ключом карточки врача. Кого нет в файле — тот ничего не получает.

Отправка идет в фоне через свой отдельный Celery только для расписания. Загрузка ставит задачу по номеру версии после сохранения и сразу отвечает администратору. Если брокер недоступен, загрузка все равно успешна. В пуше нет медицинских данных, только факт готовности и ссылка на дату и филиал.

## Адрес сервера: сейчас http, потом домен и https

Пока WebView открывает тестовый адрес по http с IP и портом. Это осознанно для проверки. В проде будет домен и https.

Что поменяется при переезде: только значение базового адреса в приложении и в настройках сайта. Логика привязки, сопоставления и рассылки не меняется. Куки тогда станут защищенными, а разрешение на открытый http в приложении можно будет убрать. Файл `google-services.json` при смене адреса менять не надо, он привязан к приложению, а не к адресу сайта.

## Как проверяем на двух телефонах

Два телефона Иванова получают оба. Общий телефон Иванова и Петрова получает только текущий. Переустановка дает новый адрес, старый чистится после ответа Firebase. Выход гасит привязку. Врач, которого нет в файле, ничего не получает.

## Как завести Firebase

Проект создается один раз, дальше только кладем файлы и переменные.

1. Зайди на `console.firebase.google.com` и создай проект, например `clinic-schedule`. Google Analytics для пушей не нужен, можно выключить. Отдельных денег для наших объемов не надо.

2. Добавь в проект Android-приложение. Package name должен совпасть с нашим каркасом один в один: `ru.sanaterra.schedule`. Nickname любой, например «Расписание врачей». SHA-1 для обычных пушей не обязателен, можно пропустить.

3. Скачай `google-services.json` и положи его в проект по пути `android/app/google-services.json`. В репозиторий он не коммитится, он уже внесен в `.gitignore`. Без него приложение соберется, но Firebase не заведется. После этого пересобери приложение в Android Studio.

4. Проверь раздел Project settings → Cloud Messaging. Нужен современный API v1, в новых проектах он включен по умолчанию. Сами уведомления слать из консоли не надо, их шлет Django кодом.

5. Сделай ключ для Django: Project settings → Service accounts → Generate new private key. Скачается JSON. Это самый секретный файл схемы. Положи его только на сервер в `/home/clinic/clinic_schedule/.firebase-service.json` с правами `600`. В архив деплоя и в git он не входит, сборка его уже исключает.

6. Пропиши на сервере в `.env`: `PUSH_ENABLED=1`, `FIREBASE_CREDENTIALS_FILE` с путем из прошлого шага, `FIREBASE_PROJECT_ID=clinic-schedule-96bf3` (фактический ID проекта из `google-services.json`), плюс свой Celery Redis из `.env.example`. Очередь не трогаем. Дальше рестарт `clinic-schedule` и старт `clinic-schedule-celery` по разделу из `deploy/DEPLOY.md`.

7. Проверь связку: войди через приложение на двух телефонах, в админке Django в разделе PushDevice должны появиться две строки. Залей тестовое расписание с этим врачом в файле — на оба должен прийти пуш. По нажатию должен открыться тот же WebView на дате расписания.

Если пуш не пришел, смотри по цепочке: есть ли адрес в админке (значит мост и endpoint работают), что пишет воркер Celery (значит задача дошла), и только потом Firebase. Чаще всего виноваты не тот package name, забытый `google-services.json` или `PUSH_ENABLED=0`.

## Если телефон не получает номер (logcat)

Симптом: в logcat от `FirebaseMessaging` — `Failed to get FIS auth token`,
`Firebase Installations Service is unavailable`, страница адрес не отправляет,
в PushDevice пусто. Проверять так:

1. Package в Firebase-приложении ровно `ru.sanaterra.schedule`, SHA-1 отладочной
   подписи добавлен как fingerprint. SHA-1 можно сверить с собранным APK:
   `apksigner verify --print-certs app-debug.apk`.
2. В Cloud Console у ключа разрешены Firebase Installations API
   (и нет чужих application restrictions). Ключ в скачанном `google-services.json`
   должен совпадать с ключом в консоли.
3. На телефоне автоматические дата и время, Google Play Services обновлены.
4. После любых правок в консоли ждать от 5 минут (настройки расходятся
   не мгновенно) и **переустанавливать приложение**: Firebase кэширует жесткий
   отказ (`FIS_AUTH_ERROR. Won't retry`) и сам повторять не будет.
5. Проверить в обход телефона: прямым запросом к FIS REST с компьютера
   (ключ + package + SHA-1). Ответ 200 — серверная часть в порядке,
   виноваты телефон или его сеть. Ответ 403 — смотреть причину в теле ответа.
6. Сравнить Wi-Fi и мобильную сеть: номер от Firebase не зависит от нашего
   сервера, он должен приходить на любой сети. Если на мобильной есть,
   а на Wi-Fi нет — режет роутер. Но сама привязка в Django возможна только
   там, где виден наш сервер (локальный IP — только домашний Wi-Fi).

## Как собрать APK

APK собирается не здесь в терминале, а в Android Studio: на текущей машине нет Android SDK и Gradle, а для сборки нужен Java 17.

1. Поставь Android Studio и открой в нем папку `android/` из проекта.
2. Положи `google-services.json` в `android/app/google-services.json`.
3. Проверь базовый адрес в `MainActivity` (сейчас тестовый http с IP, позже заменим на https-домен).
4. Для проверки на своих телефонах достаточно debug-сборки: Run на подключенный телефон либо Build APK и перенос файла `app-debug.apk` на второй телефон.
5. Отдельная подпись нужна только для публикации, для пробы не нужна.

## План после запуска Android Studio

1. Открой папку `android/` (ту, где `settings.gradle`). Первый синк Gradle займет несколько минут. Предложенные SDK Platform и Build Tools ставь.
2. Положи `google-services.json` в `android/app/` рядом с `app/build.gradle` и нажми Sync Now.
3. Проверь `BASE_URL` в `MainActivity` (сейчас тестовый http с IP). Телефон должен видеть этот адрес по сети.
4. Первый телефон: включи режим разработчика и USB-отладку, подключи кабелем, выбери его сверху и нажми Run. Войди врачом — в админке Django в PushDevice должна появиться строка.
5. Дай разрешение на уведомления, иначе шторка будет молчать.
6. Второй телефон: Build → Build APK(s), забери `app-debug.apk` из `app/build/outputs/apk/debug/`, поставь и войди. Проверь вторую строку в админке.
7. Залей тестовое расписание с этими врачами — пуш должен прийти на оба. Нажатие открывает тот же WebView на дате. Потом проверь общий кейс: выйди на одном, войди другим врачом, залей расписание первого — на этот телефон приходить не должно.

Если не собирается — смотри вкладку Build (обычно SDK или нет `google-services.json`). Сайт не открывается — телефон не видит IP:порт. Адреса нет в админке — смотри logcat по `FirebaseMessaging` и доступность `/api/push/register/`.

## Как все выглядит целиком

Врач ставит приложение. Firebase выдает установке адрес. Приложение открывает сайт. Врач входит. Страница передает адрес серверу. Сервер запоминает: этот адрес принадлежит этому врачу.

Администратор загружает расписание. Сервер сохраняет его, находит по названиям колонок тех врачей, кто в файле, берет их активные адреса и просит Firebase доставить им уведомление. Врач нажимает на уведомление и попадает в приложении на страницу своего расписания.

Центр всей системы — Django. Телефон показывает сайт и принимает пуши. Firebase только разносит сообщения.

## Как ходит токен: все части и связи подробно

### Зачем два JSON-файла (и чем они отличаются)

Файла два, и путаются они постоянно, хотя роли у них противоположные.

Первый — `google-services.json`. Это визитка приложения для Firebase: номер проекта, ID приложения, открытый API-ключ. Он запекается в APK при сборке (поэтому после его замены нужна пересборка) и говорит Firebase: «я — приложение Расписание врачей из проекта clinic-schedule». Секрета в нем нет — такой же ключ лежит в каждом установленном приложении. Хранится в `android/app/`, в git не коммитится.

Второй — service account JSON (локально `.firebase-service.json`). Это наоборот пропуск сервера: он дает Django право просить Firebase «доставь вот это вот туда». Кто владеет этим файлом — тот может слать пуши от имени проекта. Поэтому он живет только на сервере с правами `600`, в git и в архив деплоя не входит. Телефону он не нужен и никогда на телефон не попадает.

Коротко: первый доказывает Firebase, кто просит номер (приложение), второй — кто просит доставить (сервер).

### Как рождается токен (телефон и Firebase, без Django)

1. Приложение запускается. В `MainActivity.onCreate` и при каждом возврате
   на экран (`onResume`) вызывается `refreshRegistration()`: запрос
   `FirebaseMessaging.getInstance().token`.
2. Запрос уходит не на наш сервер, а в Google Play Services на телефоне,
   а оттуда — в Firebase Installations (FIS). FIS проверяет тройку
   «API-ключ + package + SHA-подпись» (все из `google-services.json`
   и подписи APK). Если тройка сошлась — выдает токен установки (FCM
   registration token). Если нет — в logcat падает `FIS_AUTH_ERROR`,
   и дальше ничего не работает.
3. Полученный токен кладется в память приложения
   (`cachedRegistration`). На этом этапе Django о нем еще ничего не знает,
   в интернет с ним телефон не ходит.

### Мостик между страницей и приложением (JS ↔ Kotlin)

Страница внутри WebView и приложение — два разных мира. Видит страница
только то, что приложение ей явно показало: объект `AndroidBridge`
с единственным методом `getPushRegistration()` (пометка
`@JavascriptInterface`). Вызов синхронный и локальный: JS спрашивает —
Kotlin отдает строчку из памяти. Никакой сети в этом вызове нет.

Мост открыт только нашему сайту: WebView грузит исключительно наш
`BASE_URL`, чужие страницы туда не попадают и мостом воспользоваться
не могут.

### Что делает страница (base.html)

Скрипт в `base.html` (значит, он есть на всех страницах, включая
расписание врача) работает так:

1. `bridgeRegistration()` — забирает строчку у моста. Если Firebase номер
   еще не выдал, получает пусто и ничего не шлет.
2. `registerWithRetries()` — пробует сразу, потом через 3 и 10 секунд:
   токен приходит асинхронно и может опоздать к загрузке страницы.
3. Когда строчка есть — обычный `fetch POST /api/push/register/`
   с телом `{registration, platform: "android"}`. Кука сессии и CSRF
   прикладываются сами, как в браузере.
4. При отправке формы выхода — `POST /api/push/unregister/` с тем же
   токеном: устройство отвязывается, чужой врач пуши не получит.

Страница сообщает только сам номер. Ни логина, ни фамилии врача в запросе
нет — и это специально.

### Что Django делает с этим запросом

Эндпоинт `POST /api/push/register/` (в `api/views.py`) делает три вещи:

1. Берет владельца не из запроса, а из сессии: кто залогинен — тот
   и владелец. Анонимов отшивает.
2. Ищет устройство по самому токену (`registration` уникален).
   Нашел — переписывает владельца на текущего (так общий телефон
   переходит от врача к врачу) и обновляет `last_seen_at`.
   Не нашел — создает запись `PushDevice` с `platform=android, active=True`.
3. Отвечает 200. Все. Дальше запись просто лежит и ждет рассылки.

`POST /api/push/unregister/` гасит запись (`active=False`).

### Что Django делает при загрузке расписания

1. Любая из трех загрузок (Web, API, интеграция) после успешного сохранения
   версии ставит задачу `send_schedule_push_task` через `queue_schedule_push`
   внутри `transaction.on_commit` — то есть только если версия реально
   сохранилась. Локально при `CELERY_TASK_ALWAYS_EAGER=1` задача выполняется
   сразу, на проде — воркером Celery.
2. `recipients_for_version()` берет ключи колонок версии (`DoctorColumn.key`)
   и ищет профили врачей с такими же `schedule_key`. Оба ключа хранятся
   уже нормализованными (`normalize_doctor_key`: нижний регистр, без точек,
   пробелов, ё→е), поэтому сравнение точное, `__in`. Кого нет в файле —
   того нет в получателях.
3. Для найденных врачей берутся только активные устройства из `PushDevice`.
4. `send_to_registrations()` шлет через `firebase_admin` (авторизация —
   service account JSON) пачками по 500. Адреса, про которые Firebase сказал
   «больше не существует», гасятся (`active=False`).
5. Сообщение содержит только заголовок «Расписание опубликовано», текст
   с датой и служебные данные с целевым URL — никаких медицинских данных.

### Как пуш превращается в открытый экран (обратный путь на телефон)

1. Firebase доставляет сообщение в Play Services, те будят приложение:
   `PushService.onMessageReceived` (работает, даже если приложение закрыто).
2. Сервис строит системное уведомление с заголовком и текстом, а внутрь
   кладет `PendingIntent`: открыть `MainActivity` с целевым URL из данных.
3. Врач тапает — открывается приложение, `MainActivity` грузит целевой URL
   в том же WebView. Жива сессия — сразу расписание, нет — сначала вход.
4. На Android 13+ для шторки нужно разрешение `POST_NOTIFICATIONS` —
   приложение спрашивает его при первом запуске.

## Полный порядок запуска (как прошли 18.09.2026)

1. Создать Firebase-проект (`clinic-schedule-96bf3`), добавить Android-приложение
   с package `ru.sanaterra.schedule`, внести SHA-1 отладочной подписи
   (`0A:B2:14:9E:3F:AB:3A:F3:D2:30:CE:8A:5D:5E:64:F6:6E:AC:E7:4D`).
2. Скачать `google-services.json`, положить в `android/app/` (и в рабочую копию
   для сборки, см. ниже). Проверить: App ID и package совпадают с консолью.
3. В Cloud Console проверить ключ `Android key (auto created by Firebase)`:
   разрешен Firebase Installations API, чужих ограничений нет.
4. Сгенерировать service account JSON, положить вне git, прописать в `.env`:
   `PUSH_ENABLED=1`, `FIREBASE_CREDENTIALS_FILE`, `FIREBASE_PROJECT_ID`.
   Плюс `ALLOWED_HOSTS` с IP машины для теста по Wi-Fi.
5. Поднять Django на `0.0.0.0:8000`, открыть в браузере телефона локальный
   адрес для проверки доступности (на телефоне нельзя `127.0.0.1`).
6. Собрать приложение в Android Studio (Gradle 8.7 под AGP 8.5.2, JDK 17).
   Путь проекта без кириллицы: из-за русских букв в пути репозитория сборка
   падает, поэтому собирается копия `C:\schedule-android\`, а правки потом
   синхронизируются обратно в `android/`.
7. Поставить на телефон, дать разрешение на уведомления, войти врачом.
8. Проверить бейдж `Push:` сверху: `токен получен` — Firebase выдал номер.
   Тап по бейджу показывает полный токен и копирует его.
9. Проверить админку Django → Push-устройства: появилась строка врача.
   Нет строки — смотреть logcat по `FirebaseMessaging`/`FIS` (раздел выше).
10. Отправить тестовый пуш: либо из Django вызовом отправки на адрес врача,
    либо из консоли Firebase тестовым сообщением на скопированный токен.
    Уведомление должно прийти в шторку на любой сети.
11. Боевая проверка: залить расписание с колонкой этого врача — должен прийти
    пуш «Расписание на завтра доступно», нажатие открывает страницу расписания.
